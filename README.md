# DotaWardPrediction

Учебный ML-пайплайн для предсказания зоны установки вражеского Observer Ward в Dota 2: из событий матча на момент `T` собирается снимок признаков, координаты установленного варда отображаются в одну из 64 ячеек сетки 8×8, поверх этого обучается CatBoost-классификатор. Вероятности классов преобразуются в нормированную тепловую карту 8×8 (Gaussian blur) для возможного отображения в UI.

Это исследовательский каркас обучения и inference-функций, а не готовый сервис. UI, HTTP/API, live-интеграции и развёртывания нет.

## Что уже работает

- Загрузка реальных реплеев Dota 2 (`.dem`) через [gem-dota](https://pypi.org/project/gem-dota/) с **честным туманом войны** — колонка видимости заполняется authoritative-событиями из самого реплея, симуляция не нужна.
- Автоматический сбор и кэширование реплеев (`collect_dataset.py`, `cache_parse.py`) — OpenDota API → `.dem` → `.json` кэш; парсинг занимает 1,5–3 минуты на матч, кэш грузится за секунды.
- Построение 21 признака на каждую установку варда (или 18 в режиме `--live-only` без replay-only покупок врага): экономика, последняя видимая позиция вардера, time_unseen, дистанции до башен/рошана/мучителей, локальная активность, покупки вардов.
- Отдельный inference-построитель снимков (`build_snapshots`) и CLI `predict.py` для предсказания тепловой карты в произвольный момент игры `T` без привязки к `obs`-событиям.
- Обучение CatBoost с групповым разбиением по матчам, балансировкой классов и опцией `--live-only`.
- Метрики качества на отложенных матчах: Top-1/Top-3 против трёх baselines (частотный, равномерный, «клетка последней позиции»), в том числе с разбивкой по фазам игры (`early` / `mid` / `late`).
- Экспортирование координат башен/рошана/мучителей из реплеев (`extract_buildings.py`) — конфиг откалиброван на patch 7.4x.
- Синтетические тесты без внешних данных + сквозная проверка и первый замер качества на 98 реальных про-матчах (3 843 снэпшота).

**Чего нет:** модели, уверенно бьющей baseline «последней позиции» по Top-1 (см. результаты и TODO ниже), большого датасета на 300–500+ матчей, подключения к live-данным (GSI/live-парсер), UI.

## Как устроен проект

```text
wardpred/
  config.py     — все константы: окна, сетка карты, координаты башен и landmarks,
                  предметы вардов, день/ночь
  loader.py     — JSONL-лог -> MatchEvents (старый путь, требует готовый visible-флаг)
  gem_loader.py — .dem/.json реплей -> MatchEvents через gem-dota, 2 перспективы
                  на матч, видимость из реплея
  features.py   — build_snapshots (произвольный T) и build_match_features (вокруг obs)
  model.py      — CatBoost: веса классов, обучение по матчам, evaluate_quality
                  (в т.ч. по фазам игры), тепловая карта
train.py        — CLI обучения: сборка датасета + обучение (--live-only) + метрики
predict.py      — CLI inference: тепловая карта и Top-K клеток в произвольный момент T
collect_dataset.py — автоматический сбор: OpenDota API -> .dem -> .json кэш
cache_parse.py  — пакетный парсинг .dem -> JSON-кэш
extract_buildings.py — entity-экстрактор позиций башен/рошана/мучителей из .dem
probe_fog.py    — валидация видимости (доля тумана, день/ночь)
check_gem_adapter.py — сквозная проверка адаптера на реальном реплее
tests/          — синтетические тесты пайплайна и модели
replays/        — реальные матчи (.dem + .json кэши) — только локально (в .gitignore)
```

Поток данных:

```text
OpenDota API --(collect_dataset.py)-->  .dem --(gem.parse, ~3 мин)-->  .json кэш
.json --(gem_loader)-->  MatchEvents × 2 перспективы
MatchEvents --(features)-->  снимки: 21 признак (18 в --live-only) + целевая ячейка (0..63)
снимки --(train.py)-->  ward_model.cbm + ward_model_meta.json + метрики
модель + снимок --(predict.py / predict_heatmap)-->  тепловая карта 8×8
```

**Почему две перспективы на матч:** для каждой команды-наблюдателя целевыми являются варды вражеской команды, а признаки видимости считаются от её лица. `match_id` у обеих перспектив одинаковый, поэтому групповое разбиение не разведёт снимки одного матча в train и validation.

## Быстрый старт

### 1. Собрать и закэшировать реплеи

```bat
.venv\Scripts\python.exe collect_dataset.py --limit 100 --workers 4 --out-dir replays
```

Скрипт забирает свежие матчи из OpenDota (`/api/proMatches` или `--source parsed` с пагинацией), скачивает `.dem` через `gem.fetch_replay`, параллельно парсит в `.json` кэш и по умолчанию удаляет сырой `.dem` (флаг `--keep-dem` оставляет `.dem`). Для сбора на нескольких ПК поддерживаются `--dump-ids`, `--ids-file` и `--shard i/N`. Реплеи Valve живут ~2 недели.

Если `.dem` уже скачаны вручную:

```bat
.venv\Scripts\python.exe cache_parse.py "replays\*.dem"
```

### 2. Обучить

```bat
.venv\Scripts\python.exe train.py "replays\*.json" --workers 4
.venv\Scripts\python.exe train.py "replays\*.json" --workers 4 --live-only
```

На двух матчах обучение запустится, но это только проверка работоспособности — для осмысленной модели нужны сотни матчей (см. TODO).

`train.py` принимает `.jsonl` (старый формат), `.dem` (парсит на лету, медленно) и `.json` (кэш). Аргументы: `--workers` (процессы для сборки датасета), `--live-only` (исключить replay-only покупки врага), `--model-out`, `--meta-out`.

### 3. Предсказать тепловую карту (CLI и Python API)

Через CLI в произвольный момент игры `T` (в секундах) для вражеского слота `0..9`:

```bat
.venv\Scripts\python.exe predict.py replays\9097129353.json --time 900 --slot 9 --top-k 3
```

Или программно из Python:

```python
import json
import numpy as np
from catboost import CatBoostClassifier

from wardpred import build_snapshots, load_match_gem
from wardpred.model import predict_heatmap

model = CatBoostClassifier()
model.load_model("ward_model.cbm")
with open("ward_model_meta.json", encoding="utf-8") as fh:
    meta = json.load(fh)

match = load_match_gem("replays/9097129353.json")[0]
snap = build_snapshots(match, np.array([900.0]), np.array([9]))
heatmap = predict_heatmap(model, snap[meta["feature_cols"]])  # массив 8x8, сумма 1
```

## Туман войны: как это решено

Задача «какие координаты врага были видны нам» в общем виде не решается из табличных данных релево (рельеф, деревья, геометрия карты). В этом проекте она решена не симуляцией, а **чтением authoritative-состояния видимости из реплея**: gem-dota выдаёт события `hero_visibility_at(team, tick)` для каждого героя. Валидация на про-матче: своя команда видна себе на 100%, вражеские герои — 20–47% времени, саппорты прячутся больше всех, ночью видимость ниже дневной.

Для позиций, не покрытых геройской видимостью, gem предоставляет геометрическую модель `assess_point_vision` (радиусы героев 1800/800, варды 1600, lifetimes вардов) — не используется, но доступна как запасной вариант.

Важно: jsonl-путь требует, чтобы `visible`-флаг готовил внешний парсер. Если его нет и скормить full-parse координаты, признаки `last_x/time_unseen` становятся утечкой (код предупреждает об этом).

## Метрики качества

После обучения автоматически считается `evaluate_quality()` на отложенных матчах (тот же сплит, что при обучении), включая разбивку по фазам игры (`early` < 10 мин, `mid` 10–25 мин, `late` ≥ 25 мин):

- **Top-1 / Top-3** — доля снэпшотов, где истинная клетка попала в топ-K вероятностей модели;
- **frequency** — baseline: предсказать самые частые клетки train-части;
- **равномерно** — теоретический уровень случайного угадывания (1/64, 3/64);
- **клетка последней позиции** — baseline: предсказать клетку последнего видимого положения вардера (с покрытием).

Значения пишутся в `metrics` JSON-метаданных рядом с моделью. Сохраняйте `.cbm` и метаданные вместе — в JSON записан порядок признаков, нужный для inference.

### Первые результаты на 98 реальных про-матчах

Датасет: **98 матчей** (`/api/proMatches`, patch 7.4x) → **3 843 снэпшота** (в среднем 39.2 на матч), покрыты все **64/64 клеток** (min=1, median=50, max=203). Отложенная валидация по `match_id` (20% матчей): **n = 780 снэпшотов** (исключён 1 снэпшот с невиданным в train классом).

| Модель / Baseline | Top-1 | Top-3 | Примечание |
|---|---:|---:|---|
| Равномерный (`uniform`) | 0.016 | 0.047 | 1/64 и 3/64 |
| Частотный (`frequency`) | 0.040 | 0.104 | самые частые клетки train |
| CatBoost `--live-only` (18 фич) | 0.127 | 0.278 | `best_iteration = 144` |
| CatBoost `full` (21 фича) | 0.132 | 0.310 | `best_iteration = 257` |
| Baseline `last_position` | **0.157** | — | клетка последней видимой позиции (покрытие 94%) |

Разбивка по фазам игры (`full` / `live-only`):

| Фаза | n | Model Top-1 (full / live) | Model Top-3 (full / live) | Freq Top-1 / Top-3 | `last_position` Top-1 (покрытие) |
|---|---:|---:|---:|---:|---:|
| `early` (< 10 мин) | 212 | 0.151 / 0.146 | 0.349 / 0.335 | 0.038 / 0.099 | **0.206** (78%) |
| `mid` (10–25 мин) | 264 | 0.125 / 0.114 | 0.303 / 0.261 | 0.061 / 0.110 | **0.148** (100%) |
| `late` (25+ мин) | 304 | 0.125 / 0.125 | 0.289 / 0.253 | 0.023 / 0.102 | **0.138** (100%) |

**Диагностика (почему `last_position` пока бьёт модель по Top-1):**
1. **Переобучение на `slot` и `hero_id`**: по Feature Importance на `hero_id` (28.8%) и `slot` (27.7%) приходится **56%–59% всей важности**, тогда как `last_x`/`last_y` получают лишь 6%–7%. На ~3 000 train-примерах и 64 классах `slot` (шумный прокси команды) и высококардинальный `hero_id` приводят к быстрому переобучению (`learn=0.038` vs `test=0.075` уже к 144-й итерации).
2. **Агрессивная балансировка весов (`sqrt`, `cap=25`) + `MultiClassOneVsAll`**: завышение весов редких клеток делает распределение вероятностей слишком «плоским» (например, на инференсе при `time_unseen=6 с` топ-3 клетки получают по ~0.035), что напрямую снижает невзвешенный Top-1.
3. **Нет явного признака `last_cell` и вектора движения**: деревьям приходится аппроксимировать сетку 8×8 через сплиты по `last_x`/`last_y`.
4. **Границы карты `±6800`**: в реальных реплеях patch 7.4x варды ставятся до `y = -8157`, т.е. внешние варды расширенной карты схлопываются в крайние клетки.
5. **Переносимость в live**: отказ от replay-only покупок врага (`--live-only`) стоит всего −0.5 п.п. Top-1 и −3.2 п.п. Top-3 — модель жизнеспособна без combatlog-покупок.

## Главные правила без утечек

1. В снимок на момент `T` входят только данные с `time <= T`; границы окон включительны.
2. `obs`-события не используются как источник признаков.
3. Позиции врага — только из видимых срезов; путь через gem решает это authoritatively.
4. Разбиение train/validation строго по `match_id` (GroupShuffleSplit), перспективы одного матча сохраняют общий id.
5. Покупки врага из combatlog — replay-only информация: на реальных live-данных такой признак придётся убрать или заменить, иначе модель будет недостижима в live (см. TODO).
