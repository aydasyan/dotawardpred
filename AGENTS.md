# Руководство для AI-агентов

## Обзор проекта

DotaWardPrediction — учебный ML-пайплайн на Python для предсказания зоны установки вражеского Observer Ward в Dota 2. Для каждого события `obs` в момент `T` код собирает снимок признаков из событий матча, отображает координаты варда в одну из 64 ячеек сетки 8×8 и обучает CatBoost-классификатор. Вероятности классов можно преобразовать в нормированную тепловую карту 8×8 с Gaussian blur для последующего отображения в UI.

Это локальный исследовательский код обучения и inference-функций, а не готовый сервис. В репозитории нет UI, HTTP/API-сервера, схемы live-интеграции, примеров реальных данных или процесса развёртывания.

Основная документация, docstring'и и комментарии написаны по-русски; сохраняйте этот язык при изменении проекта.

## Структура и поток данных

- `wardpred/config.py` — неизменяемый dataclass `WardConfig` и `DEFAULT_CONFIG`: размеры окон, сетка карты, нормализация координат, предметы вардов, фазы дня/ночи, landmarks и позиции башен. Здесь также перечислены поддерживаемые типы combatlog-событий.
- `wardpred/loader.py` — потоково читает один JSONL-файл матча в `MatchEvents`: пять pandas DataFrame (`intervals`, `purchases`, `deaths`, `obs`, `buildings`). `match_id` равен имени файла без расширения. Используется `orjson`, а при его отсутствии — стандартный `json`.
- `wardpred/gem_loader.py` — адаптер gem-dota: `.dem` (через `gem.parse`, медленно) или `.json` (кэш `gem.to_json`) в MatchEvents. Колонка `visible` заполняется authoritative-видимостью реплея (`gem.hero_visibility_at`). Один матч раскрывается в ДВА MatchEvents (по перспективе каждой команды) с ОДИНАКОВЫМ `match_id` — это обязательное условие корректного группового разбиения. Координаты gem (0..32768) переводятся в world units вычитанием 16384 (`GEM_COORD_OFFSET`). Импорт `gem` локальный — пакет опционален для JSONL-пути.
- `wardpred/features.py` — строит по одному снимку на каждое дедуплицированное `obs`-событие. Содержит `FEATURE_COLS`, преобразование `xy_to_cell`, rolling-окна и last-known-позиции. Итоговый DataFrame имеет порядок колонок `FEATURE_COLS + ["cell", "ward_x", "ward_y", "match_id"]`.
- `wardpred/model.py` — обучение CatBoost, балансировка классов, кастомная `TopKAccuracy`, сохранение метаданных и функции `predict_heatmap` / `proba_to_heatmap` / `evaluate_quality` (Top-K против baselines на том же сплите, результаты пишутся в мету).
- `wardpred/__init__.py` — публично экспортирует конфигурацию, загрузчик, построение признаков и `FEATURE_COLS`; функции модели импортируются из `wardpred.model`.
- `train.py` — CLI: расширяет glob-пути, параллельно или последовательно собирает признаки по файлам (`.jsonl`, `.dem`, `.json`), объединяет их, обучает модель и сохраняет артефакты.
- `tests/test_smoke.py` — синтетический сквозной тест JSONL → загрузка → признаки, без обучения CatBoost.
- `tests/test_model.py` — синтетический тест весов классов, обучения, предсказания и тепловой карты.
- `requirements.txt` — единственный файл зависимостей и основной конфигурационный файл окружения.
- `README.md` — подробное описание фактического состояния, формата данных, запуска, inference, ограничений и главных правил защиты от утечек.

Поток обучения: `JSONL → load_match → MatchEvents` или `.dem/.json → load_match_gem → MatchEvents (×2 перспективы)`, далее `→ build_match_features → DataFrame → train_ward_classifier → ward_model.cbm + ward_model_meta.json`.

## Окружение, сборка и запуск

Проект не является устанавливаемым пакетом: `pyproject.toml`, `setup.py`, `setup.cfg` и lock-файл отсутствуют. Отдельной сборки нет; запуск выполняется из корня репозитория. В каталоге есть локальное `.venv`, команды README используют его Windows-интерпретатор.

Установка зависимостей в выбранное окружение:

```bash
python -m pip install -r requirements.txt
```

Заявлены минимальные, но не фиксированные версии: NumPy 1.24+, pandas 2.0+, SciPy 1.10+, scikit-learn 1.3+, CatBoost 1.2+, orjson 3.9+, gem-dota 0.14+ (опционально, только для пути через реплеи). Версия Python в requirements не закреплена.

Обучение по одному или нескольким файлам/glob-шаблонам (`.jsonl`, `.dem`, `.json`):

```bash
.venv\Scripts\python.exe train.py data\*.jsonl --workers 4
.venv\Scripts\python.exe train.py replays\*.json --workers 4
.venv\Scripts\python.exe train.py data\matches\*.jsonl --model-out ward_model.cbm --meta-out ward_model_meta.json
```

Аргументы CLI:

- `matches` — обязательный список локальных файлов матчей или glob-шаблонов;
- `--workers` — число процессов для сборки датасета, по умолчанию `1`; значения больше `1` включают `ProcessPoolExecutor`;
- `--model-out` — путь CatBoost-модели, по умолчанию `ward_model.cbm`;
- `--meta-out` — путь JSON-метаданных, по умолчанию `ward_model_meta.json`.

Ошибка обработки одного матча выводится как `[skip]`, а остальные файлы продолжают обрабатываться. Если нет входных путей или ни один матч не дал `obs`-снимков, команда завершается с ошибкой. Метаданные содержат использованные признаки, категориальные колонки, присутствующие классы и `best_iteration`.

Для inference используйте `wardpred.model.predict_heatmap(model, X)`: `X` — DataFrame с одним снимком и обученными feature-колонками. Автономного inference CLI нет.

## Формат данных и модель

Загрузчик ожидает JSONL в стиле OpenDota/Clarity. Основные записи:

- `interval`: `time`/`game_time`, `slot`/`player_slot`, координаты, `gold`, `net_worth`/`networth`, `xp`, `hero_id`, необязательный `visible`;
- покупки: типы из `PURCHASE_EVENT_TYPES`, предметы из `obs_items` (`item_ward_observer` — имя в combatlog gem/OpenDota, плюс `item_observer_ward` и `item_ward_dispenser`);
- смерти: типы из `DEATH_EVENT_TYPES`;
- `obs`: время, слот и координаты установленного варда — источник целевой переменной;
- разрушения строений: типы из `BUILDING_EVENT_TYPES`.

Слоты `0..4` считаются Radiant, `5..9` — Dire. Если слот не указан явно, загрузчик пытается сопоставить имя героя с ранее встреченными interval-записями. Повреждённые JSON-строки пропускаются. Координаты вида сетки `0..127` переводятся в world units по эвристике из `loader.py`; уже мировые координаты сохраняются.

`xy_to_cell` использует row-major индексацию `0..63`: строка растёт по Y снизу вверх, колонка — по X слева направо; координаты за границами обрезаются к крайней ячейке. Целевые `obs` дедуплицируются по слоту, близкому времени и координатам в `features.py`.

В модели `slot`, `team`, `hero_id` — категориальные признаки. Разбиение train/validation выполняется только по `match_id` через `GroupShuffleSplit`, по умолчанию 20% матчей в validation. Используются `MultiClassOneVsAll`, sqrt-балансировка весов с ограничением и ранняя остановка. Классы, отсутствующие в train, удаляются из validation с предупреждением; при inference `model.classes_` необходим для правильного восстановления полной сетки 8×8. Тепловая карта сглаживается и нормализуется к сумме 1, если в ней есть ненулевая масса.

## Главный инвариант: отсутствие утечек

При любых изменениях загрузчика и признаков сохраняйте правила:

1. В снимок в момент `T` входят только данные с `time <= T`; границы rolling-окон включительны.
2. Целевой поток `obs` не используется как источник признаков. Признаки строятся из intervals, покупок, смертей и разрушений.
3. `last_x`, `last_y`, `time_unseen` рассчитываются по последним **видимым** interval-срезам. Если колонки `visible` нет, код предупреждает, что поток должен уже быть от лица наблюдателя; full-parse координаты врага создают утечку.
4. Не заменяйте групповое разбиение по матчам случайным разбиением строк: снимки одного матча не должны попадать одновременно в train и validation. Перспективы одного матча из `gem_loader.py` обязаны сохранять общий `match_id` — иначе одна и та же игра окажется по обе стороны разбиения.
5. Учитывайте разницу replay/live: покупки врага из combatlog могут быть доступны в реплее, но отсутствовать в live-интеграции.

## Калибровка и известные ограничения

Все зависимые от парсера и патча значения держите в `wardpred/config.py`, а не разносите по алгоритмам. Перед работой с реальными данными проверьте систему координат, landmarks, башни, фазы дня/ночи и длины окон.

Текущие координаты башен и landmarks извлечены entity-экстрактором (`extract_buildings.py`) из реплеев patch 7.4x — это сверенная калибровка, а не примеры, но она привязана к конкретной карте: смена патча требует пересборки (`python extract_buildings.py replays/*.dem` с правкой имени реплея внутри скрипта). Окна 60/120 с и радиус 1500 — конструктивные гиперпараметры, не калибровка патча. День/ночь (фаза 300 с) сверена с циклом gem.

## Стиль кода

- Python с аннотациями типов и `from __future__ import annotations`; конфигурация — frozen dataclass, потоки матча — dataclass.
- pandas DataFrame служат табличным контрактом между модулями; вычисления по возможности векторизованы через NumPy (`searchsorted`), а локальное геометрическое окно использует `deque`.
- Централизуйте новые признаки в `FEATURE_COLS` и сохраняйте канонический порядок выходных колонок. Категориальные признаки дополнительно отражайте в `CAT_FEATURES` и метаданных модели.
- Отсутствующие позиционные данные обычно преобразуются в маркер `-1.0`, а `time_unseen` ограничивается конфигурацией; не допускайте непредусмотренных NaN в итоговом векторе признаков.
- Приватные вспомогательные функции начинаются с `_`. Соблюдайте существующие русскоязычные docstring'и, четырёхпробельные отступы и компактные именованные параметры.
- Конфигурации линтера, форматтера, type-checker'а и pre-commit в репозитории нет. Не вводите новые зависимости или инструменты без необходимости.

## Тестирование

Канонические проверки — два самостоятельных скрипта с обычными `assert`, без тестового фреймворка и внешних данных:

```bash
.venv\Scripts\python.exe tests\test_smoke.py
.venv\Scripts\python.exe tests\test_model.py
```

Ожидаемые финальные строки — `SMOKE OK` и `MODEL SMOKE OK`. Первый тест быстро проверяет загрузку, нормализацию координат, дедупликацию, rolling-признаки (включая границу локального окна: событие ровно на T−60 остаётся, старше — нет), hero_id строго на момент T и отсутствие NaN. Второй обучает небольшую CatBoost-модель на синтетическом датасете и проверяет тепловую карту и `evaluate_quality` (радиусы значений, покрытие baseline'а последней позиции); он выводит журнал обучения и может выдавать предупреждения о редких классах. Тесты самостоятельно добавляют корень репозитория в `sys.path`.

`pytest` не объявлен зависимостью и не настроен. Для новых проверок следуйте существующему стилю: детерминированный генератор случайных чисел, синтетические данные, обычные `assert`, вызов тестовых функций из блока `__main__`. После изменения признаков обязательно проверяйте как временную границу `T`, так и групповое разбиение по матчам.

## Безопасность и развёртывание

Код работает с локальными JSONL и создаваемыми локально артефактами; сетевых вызовов, секретов, учётных данных и конфигурации окружения в проекте нет. Главный риск корректности — утечка невидимой игроку информации в признаки, описанная выше.

CI, контейнеризация, release-процесс и deployment-конфигурация отсутствуют. Результат запуска `train.py` — CatBoost-файл модели и JSON-метаданные; сохраняйте их вместе, поскольку метаданные описывают порядок признаков и присутствующие классы. Автоматического экспорта в приложение или UI не реализовано.
